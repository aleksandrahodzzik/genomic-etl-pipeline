Generated by `scripts/benchmark.py`; every number below was measured on the machine described here, in one session. Re-run it to reproduce.

## Exact commands

```
make up
uv run python scripts/benchmark.py --data-dir data/bench
```

`make bench` first runs the data generator with:

```
uv run python scripts/generate_data.py --contigs 3 --contig-length 5000000 --variants 1000000 --titv 2.0 --error-rate 0.005 --seed 42 --out-dir data\bench
```

Dataset: 1,000,000 VCF records (5,000 deliberately invalid) on 3 contigs of 5,000,000 bp, producing 1,089,328 normalized variant rows. CHUNK_SIZE = 100,000 records, so the file is split into 10 chunks.

## 1. Throughput vs. number of worker containers

Time from `POST /jobs` returning to the job reaching `completed` (upload excluded). Each worker container runs one Celery process (`--concurrency=1`), so N containers process N chunks at once. The same machine also runs PostgreSQL, Redis, MinIO and the API, so this is a single-host measurement of the architecture, not a cluster benchmark.

| workers | runs | wall time per run (s) | median (s) | records/s (median) | speed-up vs 1 |
|---:|---:|---|---:|---:|---:|
| 1 | 3 | 38.0, 32.7, 36.8 | 36.8 | 27,142 | 1.00x |
| 2 | 3 | 22.0, 30.5, 22.6 | 22.6 | 44,255 | 1.63x |
| 4 | 3 | 21.6, 21.2, 20.7 | 21.2 | 47,261 | 1.74x |

Per-chunk time inside a worker (median over 10 chunks of one single-worker run, from the worker logs): parse + validate + normalize **1.40 s**, COPY into PostgreSQL **1.63 s**.

## 3. Cost of keeping the indexes during bulk load

Same file, 1 worker. "With indexes" is the row from table 1; "without" dropped both secondary indexes before the job and built them afterwards.

| strategy | load (s) | index build (s) | total (s) |
|---|---:|---:|---:|
| indexes maintained during load (default) | 36.8 | 0 | 36.8 |
| drop indexes, load, then build | 31.7 | 5.8 | 37.5 |

Build times: `ix_variants_job_chrom_pos` 2.6 s, `ix_variants_job_type` 3.2 s.

## 4. How the rows get into PostgreSQL

The same 100,000 real variant rows (made by the pipeline's own parser and normalizer) inserted into a temporary table that has only a bigserial primary key, median of 3 repetitions, commit included. This isolates the insertion mechanism; the real table also maintains the two secondary indexes (section 3). The last row uses a smaller batch because it is too slow to run on all rows; its rate is measured, not extrapolated.

| method | rows | median time (s) | rows/s | vs COPY |
|---|---:|---:|---:|---:|
| COPY (what the pipeline uses) | 100,000 | 0.45 | 223,506 | 1.00x |
| psycopg executemany (pipeline mode) | 100,000 | 6.49 | 15,403 | 0.07x |
| SQLAlchemy Core insert(), batched | 100,000 | 7.83 | 12,768 | 0.06x |
| SQLAlchemy ORM add_all + commit | 100,000 | 15.89 | 6,292 | 0.03x |
| one INSERT per row, one round trip each | 10,000 | 9.59 | 1,043 | 0.00x |

## Run-to-run variation and how to read these numbers (hand-written, not regenerated by the script)

This file is the output of one `make bench` run, from a fresh clone at commit `680e845`. The same benchmark had been run earlier on the same machine, from the working tree at commit `f9dc495` plus the insert-methods change (that report is in git history, commit `a234f25`). The two sessions disagree by more than I would like, so here are both:

| | earlier session | this file |
|---|---:|---:|
| 1 worker, median | 33.7 s | 36.8 s |
| 2 workers, median | 20.5 s (1.64x) | 22.6 s (1.63x) |
| 4 workers, median | 17.5 s (1.93x) | 21.2 s (1.74x) |
| region query median, with / without index | 2.40 / 67.41 ms (28x) | 2.09 / 63.78 ms (31x) |
| keyset page, mid-job | 1.63 ms | 1.24 ms |
| `COPY` / ORM, 100k rows | 0.33 s / 14.47 s | 0.45 s / 15.89 s |
| drop indexes before load, total vs. default | 29.1 s vs. 33.7 s | 37.5 s vs. 36.8 s |

(An aborted run that crashed before it could write a report, because of the `/dev/shm` problem fixed in commit `26c89c2`, had already completed the scaling section: 1 worker 33.8 s, 2 workers 21.7 s, 4 workers 17.6 s, medians.)

What I take from this, and what I do not:

- **Stable across sessions**: the ordering of everything (more workers is faster, the index wins by roughly 30x, `COPY` beats the ORM by a wide margin) and the speed-up from 2 workers (1.63x–1.64x). Quote ratios and ranges, not single absolute values.
- **Not stable**: the 4-worker result (17.5 s to 21.2 s, 1.74x to 1.93x) and, in particular, **whether dropping indexes before a load helps**. The earlier session saved 4.6 s in total, this one lost 0.7 s. I have no measurement that explains the difference, so I make no claim that it is worth doing; the pipeline keeps the indexes on during load.
- **Scaling is sub-linear on this machine**. All containers, PostgreSQL included, share one laptop inside the Docker Desktop VM, so workers compete with the database for CPU and disk. I did not isolate which resource limits it. The job has 10 chunks, so 4 workers cannot be fully busy through the last wave either; that is arithmetic on the chunk count, not a measurement.
- **The database share of a chunk is large**: per chunk, `COPY` (1.63 s in this file, 1.43 s in the earlier one) takes about as long as parsing, validating and normalizing (1.40 s and 1.29 s).
- **`COPY` vs. the alternatives (section 4)** was measured with the database in a VM on the same host, which penalizes methods that need many round trips. On a database with different network latency the ratios will differ; the ordering is unlikely to.
- Everything is from one machine on one day; there is no multi-host measurement.
