```
make up
```

`make bench` first runs the data generator with:

```

```

Dataset: 1,000,000 VCF records (5,000 deliberately invalid) on 3 contigs of 5,000,000 bp, producing 1,089,328 normalized variant rows. CHUNK_SIZE = 100,000 records, so the file is split into 10 chunks.

## 1. Throughput vs. number of worker containers

Time from `POST /jobs` returning to the job reaching `completed` (upload excluded). Each worker container runs one Celery process (`--concurrency=1`), so N containers process N chunks at once. The same machine also runs PostgreSQL, Redis, MinIO and the API, so this is a single-host measurement of the architecture, not a cluster benchmark.

| workers | runs | wall time per run (s) | median (s) | records/s (median) | speed-up vs 1 |
|---:|---:|---|---:|---:|---:|
| 1 | 3 | 33.9, 33.7, 31.7 | 33.7 | 29,674 | 1.00x |
| 2 | 3 | 20.5, 24.1, 20.5 | 20.5 | 48,764 | 1.64x |
| 4 | 3 | 19.1, 17.5, 17.4 | 17.5 | 57,247 | 1.93x |

Per-chunk time inside a worker (median over 10 chunks of one single-worker run, from the worker logs): parse + validate + normalize **1.29 s**, COPY into PostgreSQL **1.43 s**.

## 3. Cost of keeping the indexes during bulk load

Same file, 1 worker. "With indexes" is the row from table 1; "without" dropped both secondary indexes before the job and built them afterwards.

| strategy | load (s) | index build (s) | total (s) |
|---|---:|---:|---:|
| indexes maintained during load (default) | 33.7 | 0 | 33.7 |
| drop indexes, load, then build | 26.1 | 3.1 | 29.1 |

Build times: `ix_variants_job_chrom_pos` 1.8 s, `ix_variants_job_type` 1.3 s.

## 4. How the rows get into PostgreSQL

The same 100,000 real variant rows (made by the pipeline's own parser and normalizer) inserted into a temporary table that has only a bigserial primary key, median of 3 repetitions, commit included. This isolates the insertion mechanism; the real table also maintains the two secondary indexes (section 3). The last row uses a smaller batch because it is too slow to run on all rows; its rate is measured, not extrapolated.

| method | rows | median time (s) | rows/s | vs COPY |
|---|---:|---:|---:|---:|
| COPY (what the pipeline uses) | 100,000 | 0.33 | 306,920 | 1.00x |
| psycopg executemany (pipeline mode) | 100,000 | 4.49 | 22,286 | 0.07x |
| SQLAlchemy Core insert(), batched | 100,000 | 5.56 | 17,988 | 0.06x |
| SQLAlchemy ORM add_all + commit | 100,000 | 14.47 | 6,910 | 0.02x |
| one INSERT per row, one round trip each | 10,000 | 6.90 | 1,449 | 0.00x |

## How to read these numbers (hand-written, not regenerated by the script)

- **Scaling is sub-linear on this machine**: 2 workers give 1.64x and 4 workers 1.93x over one. All containers, PostgreSQL included, share one laptop inside the Docker Desktop VM, so workers compete with the database for the same CPU and disk. I did not isolate which resource is the limit, so I make no claim about it. The job has 10 chunks, so 4 workers cannot be fully busy through the last wave either; that is arithmetic on the chunk count, not a measurement.
- **The database share of a chunk is large**: per chunk, COPY (1.43 s) takes about as long as parsing, validating and normalizing (1.29 s). Parsing is CPU-bound and scales with workers; the COPY side contends on one PostgreSQL instance.
- **COPY vs. the alternatives (section 4)** was measured with the database in a VM on the same host, which penalizes methods that need many round trips. On a database with different network latency the ratios will differ; the ordering is unlikely to.
- **Dropping the indexes before loading** saved 7.6 s of 33.7 s here (26.1 s load + 3.1 s build = 29.1 s). The pipeline keeps them maintained by default, because chunks load concurrently and results must be queryable as soon as a chunk commits; see the README design notes.
- Numbers are from a single session on one machine: treat the ratios as more meaningful than the absolute values.
