# Benchmark on real data: ClinVar GRCh38

Generated by `scripts/benchmark_clinvar.py`. Every number below was measured on the machine described at the end, in one session; the synthetic set was measured in the same session, alternating with ClinVar run by run, so the two columns are comparable. Re-run it to reproduce.

## Inputs

- **ClinVar** release 20261025 for GRCh38 ([clinvar_20261025.vcf.gz](https://ftp.ncbi.nlm.nih.gov/pub/clinvar/vcf_GRCh38/archive_2.0/2026/clinvar_20261025.vcf.gz), MD5 `da0094ec396d77359af510591fcea70c`, checked against NCBI's `.md5`): 4,599,696 records, sites only (no sample columns).
- **Subset**: chromosomes 1, 2, 17, the 3 with the most ClinVar records: **1,094,545 records** (23.8% of the release). The other records are dropped before upload, because against this reference they would all be rejected as `unknown_contig`.
- **Reference**: GRCh38 as UCSC hg38 per-chromosome FASTA ([chr1.fa.gz](https://hgdownload.soe.ucsc.edu/goldenPath/hg38/chromosomes/chr1.fa.gz) `f069c41e7cc8c2d3a7655cbb2d4186b8`, [chr2.fa.gz](https://hgdownload.soe.ucsc.edu/goldenPath/hg38/chromosomes/chr2.fa.gz) `609cc41e8a44eb99f87839456c6ed333`, [chr17.fa.gz](https://hgdownload.soe.ucsc.edu/goldenPath/hg38/chromosomes/chr17.fa.gz) `023ccefd298db339159a446e88d742ac`; MD5s checked against UCSC's `md5sum.txt`), 574,407,392 bp. ClinVar names the contigs `1`, `2`, `17`, the reference `chr1`, `chr2`, `chr17`; the pipeline's alias map matches them, and rows are stored under the reference's names.
- **Synthetic**: the `make data` set: 1,000,000 records on 3 contigs of 5 Mb, 0.5% deliberately invalid (see [BENCHMARKS.md](BENCHMARKS.md)).

Region queries: 100 windows of 10 kb, each centred on a stored variant picked at random (so every window holds data, as when someone looks up a gene or a variant), timed directly in PostgreSQL (`WHERE job_id = ? AND chrom = ? AND pos BETWEEN ? AND ? ORDER BY pos`). "Without the index" drops `(job_id, chrom, pos)` inside a transaction that is rolled back. The API page is the same query through FastAPI for the first 30 windows, timed from the client.

**About this run.** The laptop was short of memory during this run (about 3 GB of 31 GB free, with other applications open). So that Windows would not stop it, a watcher outside the benchmark dropped the Docker VM's clean page cache (`echo 3 > /proc/sys/vm/drop_caches`) whenever free memory fell below 3.5 GB: 25 times, from the first warm-up job to the last region query, about once per job. Both datasets alternate run by run and were hit alike, but after each drop PostgreSQL re-reads pages from disk, so the absolute times are probably somewhat pessimistic, the query p95 and the queries without the index most of all. The slowest ClinVar query with the index (60 ms for 1,590 rows) is most likely such a cold read; it is the maximum, outside the median and the p95.

**Normalization cross-check.** `bcftools norm -m -any -f` (bcftools 1.21--h8b25389_0) over the same 1,094,545 ClinVar records: 0 split, 0 realigned, 0 REF mismatches. The pipeline rewrote 0 rows. Both agree that ClinVar ships its records already split, trimmed and left-aligned, so zero is the expected answer here; on the synthetic set, which contains unaligned indels on purpose, the same normalizer rewrites about a quarter of the rows.

**BRCA1** (chr17:43,044,295-43,125,483): 15,318 ClinVar variants stored; the first API page (100 rows) takes 7.8 ms (median of 10).

## Rejected ClinVar records and why

Counts are exact (from the job); the patterns and examples come from the stored rejected lines.

| reason | records | what the lines have in common | example (first 7 columns) |
|---|---:|---|---|
| `unsupported_symbolic` | 312 | ALT .: 312; HGVS g.N= (no change): 312; CLNVC Variation: 157; CLNVC single_nucleotide_variant: 146; CLNVC Deletion: 7; CLNVC Microsatellite: 1; CLNVC Indel: 1 | `1 942451 836156 T . . .`, `CLNHGVS=NC_000001.11:g.942451=` |

`ALT .` means the record has no alternate allele. In ClinVar these are submissions about the reference allele itself (the HGVS expression `g.N=` means "no change at position N"): there is no variant to normalize or store, so the pipeline refuses them as `unsupported_symbolic`, the same rule that refuses `<DEL>` or `*`.
